# NET-004 evidence report

## Result

PASS. The authenticated SignalR chat contract is implemented and the targeted automated checks passed.

## Changes

- Completed `ChatHub` operations with ticket-participant authorization and a fresh, server-side auth-session check on **every** hub invocation. A revoked or expired session is aborted and receives a `HubException`.
- Added ordered reconnect synchronization: `SyncHistory(ticketId, afterMessageId, pageSize)` returns an ascending, bounded cursor page from PostgreSQL-backed message history.
- Strengthened sends: positive ticket ID, non-empty UUID, non-empty/4,000-character body validation; client UUID de-duplication is enforced by the database unique key; a retry returns the original message without broadcasting it again.
- Added `SetTyping` for ephemeral group typing events and `MarkRead` for monotonic, durable per-user ticket read cursors.
- Added `ChatReadReceipt`, its EF mapping, and migration `20261024110000_AddChatReadReceipts`. The migration adds unique `(TicketId, ReaderId)` and history lookup indexes.
- Added chat hub integration coverage for two authorized sessions, unauthorized subscription, duplicate sends, ordered paginated reconnect recovery, persisted receipts, typing, validation, and post-connect revocation. These tests use the application's actual `TicketParticipant` authorization service with in-process hub caller/client/group doubles.
- Documented the intentionally single-instance SignalR deployment limit in `README.md`: Redis is configured as a cache only; no SignalR Redis backplane is configured.

## Remaining gaps / explicit boundaries

- No browser-driven WebSocket test, browser compatibility test, load test, or production deployment was executed.
- Redis backplane scale-out is not implemented or tested. Chat group delivery is limited to a single API instance; PostgreSQL remains authoritative for history and receipts, so reconnect recovery is durable.
- The direct hub tests validate hub behavior and authorization integration, but do not claim an end-to-end browser transport validation.

## Security notes

- Hub authorization is checked at subscription and on sends, history sync, read receipts, and typing; a handshake alone is not trusted after session revocation.
- Read cursors are scoped to a participant and cannot be moved backward by an older browser session.
- Client-provided UUIDs cannot overwrite another sender's message or altered body.
- Validation limits history page size and message body size; database constraints remain the cross-process source of truth for de-duplication and receipt identity.
- Only fictional local test data and the repository's local Compose services were used. No external services, deployments, commits, or publishes were performed.
